------------------------------------------------------------------------------
  cmd OR PowerShell? THIS TRIPS UP ALMOST EVERYONE
------------------------------------------------------------------------------

You need BOTH, for different things:

  Command Prompt (cmd)   ->  python commands
                             cd C:\AtomicLab
                             python detector.py sysmon_events.csv

  PowerShell (as Admin)  ->  anything starting with a hyphenated verb:
                             Get-WinEvent, Invoke-AtomicTest, Export-Csv
                             and running export_sysmon.ps1

If you paste a Get-WinEvent command into cmd you get:
    'Get-WinEvent' is not recognized as an internal or external command
That does NOT mean anything is broken. It means you are in the wrong shell.

How to tell which one you are in: the prompt.
    C:\AtomicLab>            <- Command Prompt
    PS C:\AtomicLab>         <- PowerShell

------------------------------------------------------------------------------
  STEP 3 - CONFIRM SYSMON IS RUNNING                  (10 min)
------------------------------------------------------------------------------

Sysmon is what records the file activity your detector reads. In Command
Prompt inside the VM:

  EXPECT: STATE : 4  RUNNING
  (it may be listed as sysmon64 - try  sc query sysmon64  as well)

      cd C:\AtomicLab
      .\Sysmon64.exe -accepteula -i

Then confirm the log exists. PowerShell as Administrator:

      Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -MaxEvents 3

  EXPECT: three recent events printed.
  IF "No events were found": Sysmon is installed but has logged nothing yet.
  Open a few files to generate activity, then try again.

  SAVE THIS: the sc query output.  -> evidence/day1_sysmon_running.txt


------------------------------------------------------------------------------
  STEP 4 - RUN THE T1486 ATOMIC TEST                  (20 min)
------------------------------------------------------------------------------

Snapshot taken? Network isolated? If not, go back to the safety section.

In PowerShell AS ADMINISTRATOR, inside the VM:

      Install-Module -Name Invoke-AtomicRedTeam -Scope CurrentUser -Force
      Import-Module Invoke-AtomicRedTeam

      # WRITE DOWN the time before you start
      Get-Date -Format "yyyy-MM-dd HH:mm:ss"

      Invoke-AtomicTest T1486 -GetPrereqs
      Invoke-AtomicTest T1486

      # WRITE DOWN the time when it finishes
      Get-Date -Format "yyyy-MM-dd HH:mm:ss"

  EXPECT: the test runs and completes. Files in the lab folder get encrypted
  or renamed - that is the point.

  WRITE BOTH TIMES DOWN. You need them for your report, and they tell you
  how far back to export in the next step.

  SAVE THIS: the two timestamps and the test output.
             -> evidence/day2_t1486_run.txt

  IF Defender blocks it: your exclusion is not set on C:\AtomicLab. Set it
      on that folder only, then re-run.
  IF the module will not install: you are not running PowerShell as

      has no internet, download the module on your host, copy it in, and keep

------------------------------------------------------------------------------
  STEP 5 - EXPORT THE EVIDENCE                        (10 min)
------------------------------------------------------------------------------

In PowerShell AS ADMINISTRATOR:

      cd C:\AtomicLab
      powershell -ExecutionPolicy Bypass -File export_sysmon.ps1

  This writes TWO files, which are your two test cases:

      sysmon_events.csv     the last 15 minutes - should contain the attack
      sysmon_baseline.csv   30-40 minutes ago - ordinary activity, your control

  EXPECT: two "wrote N events to ..." lines, both with N greater than 0.

  IF the attack window has 0 events, or your test ran longer ago than 15
  minutes, widen it:

      powershell -ExecutionPolicy Bypass -File export_sysmon.ps1 -AttackMinutes 60

  IF the baseline window has 0 events, shift it further back:

      powershell -ExecutionPolicy Bypass -File export_sysmon.ps1 -BaselineFrom 120 -BaselineTo 100

  WHY USE THE SCRIPT instead of a Get-WinEvent command: it formats the
  timestamp as yyyy-MM-dd HH:mm:ss explicitly. A plain Export-Csv writes dates
  in your machine's local format (like 30-09-2026), which detector.py cannot
  read - and it fails SILENTLY, reporting zero events with no explanation.
  The script removes that whole problem.

  SAVE THIS: the export output showing both event counts.
             -> evidence/day2_export.txt


------------------------------------------------------------------------------
  STEP 6 - DETECT, AND PROVE THE CONTROL              (15 min)
------------------------------------------------------------------------------

In Command Prompt:

      cd C:\AtomicLab
      python detector.py sysmon_events.csv

  EXPECT: CONFIRMED [High] or [Critical], naming how many file writes happened
  in one short window, a few sample file names, and the process that started
  just before the burst.

Now the negative control. SAME command, SAME settings, different file:

      python detector.py sysmon_baseline.csv

  EXPECT: CLEAN: no encryption burst found

  THIS IS THE MOST IMPORTANT RESULT IN YOUR PROJECT. You changed nothing
  between the two runs - no edited timestamps, no changed threshold. The same
  detector says CONFIRMED on the attack and CLEAN on ordinary activity. That
  is what makes it a detector and not just an alarm.

  SAVE BOTH: -> evidence/day3_alert.txt
             -> evidence/day3_negative_control.txt

  IF the attack also says CLEAN: the burst may be spread wider than 10
  seconds, or the test wrote fewer files than expected. Look at the
  "N are FileCreate" number it printed. Then try a wider window or a lower
  threshold, and SAY SO in your report - tuning a threshold against real data
  is a legitimate finding, not a failure:

      python detector.py sysmon_events.csv --window 30 --threshold 10

  IF the baseline says CONFIRMED: your baseline window overlaps the attack.
  Re-export with -BaselineFrom 120 -BaselineTo 100 and try again.


------------------------------------------------------------------------------
  STEP 7 - THE FRONTEND (LIVE VIEWER)                 (15 min)
------------------------------------------------------------------------------

index.html reads findings.json - the file detector.py just wrote - and draws
it as a colour-coded table that refreshes itself every 3 seconds.

  CRITICAL: it must be SERVED, not double-clicked. Opening the file directly
  gives a file:/// address, and browsers block a file:/// page from reading
  another file. The table would stay empty forever.

7a. Show it EMPTY first. In Command Prompt:

      cd C:\AtomicLab
      del findings.json
      del incidents.db
      python -m http.server 8000

    Leave that window running - it is a server, it is meant to look frozen.
    Open a browser inside the VM and go to:

      http://localhost:8000/index.html

  EXPECT: "No findings yet - run python detector.py ... to populate this."

  SCREENSHOT IT NOW, while it is empty.  -> evidence/day_frontend_empty.png

7b. In a NEW Command Prompt window (leave the server running):

      cd C:\AtomicLab
      python detector.py sysmon_events.csv

7c. Go back to the browser. Do not even refresh - wait 3 seconds.

  EXPECT: the finding appears on its own, with a red or dark-red severity
  cell and the burst description.

  SCREENSHOT IT.  -> evidence/day_frontend_live.png

Those two screenshots - empty, then populated by a detection you actually ran
- are the strongest slide in your presentation. They prove the screen is
driven by your real detector and your real Sysmon evidence, not sample data.

  IF the table shows an error about file:/// - you double-clicked index.html.
      Use the http://localhost:8000/index.html address instead.
  IF it stays on "No findings yet" - findings.json is not in C:\AtomicLab.
      Check with  dir findings.json  in that folder.
  IF "port already in use" - a server is already running. Use port 8001 and
      open http://localhost:8001/index.html instead.
